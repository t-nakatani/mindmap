# mindmap の検証マップ

このフォルダは、mindmap のユーザーから見える振る舞いを確かめるための、保守される手順の置き場です。アプリを動かす前にこの索引を読み、該当する機能のファイルを手順として使います。

## 前提（毎回）

- 検証用サーバーを `http://127.0.0.1:4388` で、使い捨てのデータで立てる（`preview_start {name: "mindmap-verify"}` か `$V launch`）。
- `V=.cursor/skills/verify-mindmap/scripts/verify` をリポジトリの根で定義する。
- `$V build` で CLI を作る。
- `$V doctor` を実行し、`NG` が無いことを確かめる。
- データは空から始まる。最初の画面か CLI の操作で、マップ `map`（中心ノード「中心テーマ」）が自動でできることがある。
- この検証で立てたもの以外のインスタンスは動かさない。特にポート 4381（ふだんの開発サーバー）と本番は動かさない。

## 動かし方の決まり

- CLI は必ず `$V cli <引数>` で動かす。`target/release/mindmap` を直接呼ぶと、本番の設定を読む。
- CLI の対象は、`--map verify` のように名前で決める。`use` は、画面を切り替えたいときだけ使う。
- 画面の手がかりは、ID と data 属性（`#map-btn-name`、`g.node[data-id]` など）を使う。座標や Tab の順には頼らない。
- 状態は、別の口から読み直す（`$V api GET '/api/map?name=…'`、`$V cli show`、`$V dom`）。
- 書き換えたものは、各手順の最後で消すか元に戻す。証拠は消さない。

## 証拠と、確かめられなかったことの報告

- 操作と結果の両方を残す。CLI の操作は `cli.log` に、状態は `api.log` に自動で残る。
- 画面の証拠は、`$V shot` の PNG と `$V dom` のノード一覧にする。画面の題名（`<マップ名> - Mind Map`）でアプリとマップが分かる。
- 即時反映（WebSocket）は、開いたままのページで確かめる。開き直した `shot` や `dom` では証明にならない。
- 証拠には、機能 ID（例: `node-add`）と、使った入口（CLI か画面か）を書き添える。
- 届かなかった入口は、試したコマンドと、満たせなかった前提を書いて報告する。別の入口で確かめたものを、その入口の確認として報告しない。

## 機能のファイルの決まり

各ファイルは、H1 の題名と、ユーザーから見た振る舞いを書いた1段落で始めます。続けて、次の4つの H2 をこの順に置きます。

1. `Sub-features`: 短い ID と、振る舞いを1行ずつ。
2. `How to get to it (user POV)`: ユーザーの入口をすべて。
3. `Driving it with verify`: `Preconditions:` で始め、操作・コマンド・見える結果を組にした太字ラベルの箇条書き。
4. `Gotchas`: 検証を無駄にしたり無効にしたりする落とし穴。

## 機能

- [ノードの操作](./node-ops.md): 足す・改名・移す・消す・折りたたむ・配置。CLI と画面のキー操作、画面への即時反映。
- [書き出しと取り込み](./outline.md): `show`・`export`（`/api/outline`）と、Markdown の箇条書きの `import`。
- [複数のマップ](./maps.md): `maps`・`new`・`use`、画面のマップの一覧（切り替え・作成・改名・削除）。
- [リンク](./links.md): URL のノード、`--url`・`link`・`unlink`、画面のリンクのパネル。
- [領域と共有](./spaces-sharing.md): `spaces`・`share`・`--space`。手元で確かめられる範囲と、確かめられない範囲。
